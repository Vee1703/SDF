**To:** eng-infra-leads

SBS is currently provisioned at 3x r6g.xlarge nodes, sized against the 90-minute TTL assumption from the original 2024 capacity model. # Assistant Experience — Postmortem: Attachment Write Path Latency Spike

**Incident:** INC-4471
**Date:** 2026-08-22
**Author:** Ariel Nkemdirim
**Severity:** SEV3 (no customer-facing outage, elevated ticket-filing latency for ~40 min)

## Summary

Between 14:02 and 14:41 UTC, the support attachment write path (the process that copies a session's render payload into a new ticket when a user files "Report a problem") experienced p99 write latency of 8-12s, up from a normal ~400ms. No tickets were lost; users experienced a slow spinner on submission.

## Root cause

A deploy to the support ticketing system's backend (unrelated team, unrelated change — a reindex job for search) briefly saturated the shared write-path database connection pool that the attachment copy step also uses. The attachment path isn't isolated onto its own pool, which it should be given it reads from a separate upstream system entirely (that ticket's older than my tenure, apparently, per the runbook history).

## Timeline
- 14:02 — reindex job starts, connection pool utilization climbs
- 14:09 — first elevated-latency alert fires, on-call acks
- 14:15 — on-call identifies correlation with reindex job, pages ticketing team
- 14:31 — reindex job paused
- 14:41 — latency back to baseline

## Impact
~180 ticket submissions affected, all eventually succeeded, no data loss.

## Action items
1. Isolate attachment write path onto dedicated connection pool — owner: Ariel, due next sprint
2. Add pool-saturation alert independent of the generic latency alert — owner: Ariel
3. Ticketing team to tag reindex jobs as high-risk for shared-pool deploys — owner: ticketing team, tracked in their backlog

No customer communication needed given severity and resolution time.

# Meridian Evaluation Program — Reasoning Regression Triage, Aug Incident

**Filed by:** on-call MEP eng (rotation: K. Sandoval)
**Severity:** P0 per Model Quality Council charter
**Status:** Resolved

## What happened

Nightly GPQA-diamond run on the 3.1-rc2 checkpoint showed a 2.8pt accuracy drop versus the 3.0 baseline, tripping the automated regression gate before the checkpoint could proceed to staged rollout. Gate held it correctly — this is exactly the failure mode it exists to catch.

## Investigation

Bisected against the last three training runs. Isolated to a data-mix change two runs back that increased the proportion of short-form conversational data relative to multi-step reasoning data, beyond what the mix-ratio guardrails were supposed to allow — the guardrail check itself had a stale threshold from before the last corpus rebalance.

Confirmed via ablation: reverting just the mix ratio (keeping everything else from 3.1-rc2) recovers 2.3 of the 2.8 points. Remaining 0.5pt is within normal run-to-run noise for this benchmark.

## Fix

Mix ratio guardrail threshold updated to reflect current corpus composition. 3.1-rc3 kicked off with corrected mix, GPQA-diamond back within 0.2pt of 3.0 baseline on the rc3 nightly.

## Process gap

The guardrail threshold being stale is the actual root cause — it should have failed loudly when the corpus composition changed, not silently permitted an out-of-bounds mix. Adding a check that fires when actual mix ratio deviates from the guardrail's assumed baseline by more than 5%, independent of whether it breaches the guardrail itself.

## Follow-up
Model Quality Council notified per charter, no further escalation needed given same-week resolution. Postmortem doc linked in the MQC incident index.
