**For:** all Product Engineering new hires
**Owner:** Eng Onboarding (rotates, currently maintained by L. Vasquez)

- IT ships laptop, badge activation email arrives 24h prior
- Manager should have added you to team calendar and relevant Slack channels

- 1pm: Meet with manager, review 30/60/90 doc

- Internal wiki homepage, search is decent, ask in #eng-help if you can't find something
- Org chart tool (updated weekly, can lag on very recent moves)
- Benefits/HR portal — separate from eng onboarding, HR will send this separately

## Who to ask
General eng process questions → your onboarding buddy first, manager second
Access/tooling issues → #it-help
"Is this normal" questions → literally anyone on your team, we'd rather you ask

Welcome. It gets less overwhelming by week three, roughly.

# Product Engineering — Code Review Policy, Proposal for Change

**From:** Tomas Weill
**To:** eng-leads list
**Re:** required approvals on infra-adjacent PRs

## The problem

Current policy requires one approval for any PR to merge, from anyone with write access to the repo. This works fine for most repos. It doesn't work well for the handful of repos where a change can silently break other teams' builds — shared component libraries, the internal CLI tooling repo, and a couple of shared config repos.

We've had three incidents in the last two months where a single-approval merge to a shared repo broke another team's CI, in each case reviewed and approved by someone without deep context on the downstream consumers. Nobody did anything wrong under the current rules — this is a policy gap, not a review-quality problem.

## Proposal

For a defined list of "shared-blast-radius" repos (I'd start with 4, open to more), require two approvals, at least one from a maintainer on that specific repo's CODEOWNERS list rather than just anyone with write access.

## Counterarguments I've heard already

"This slows down small fixes" — true, and the proposal includes a fast-path exception for changes under 5 lines with no changes to public interfaces, which covers the majority of small fixes people are worried about getting stuck.

"CODEOWNERS lists go stale" — also true, and a real risk. Proposing that each shared repo's CODEOWNERS list gets reviewed quarterly by that repo's owning team, same cadence as most teams already do for other ownership docs.

"Two approvals means slower merges generally" — data from the two teams already doing this informally (Search Infra, Billing Core) shows median time-to-merge only about 40 minutes slower, not the multi-day delay people assume.

## Ask

Feedback by end of next week. If there's rough consensus I'll draft the actual repo list and circulate for a final sign-off round before enabling branch protection changes.

# Postmortem: Staging Deploy Pipeline Outage, Aug 12

**Incident:** INC-4438
**Severity:** SEV2 (no production impact, ~3hr staging deploy freeze across all teams)
**Author:** Platform Infra on-call

## Summary

A change to the deploy orchestrator's config schema validation was merged and deployed to the staging control plane at 10:14am. The change was backward-incompatible with config files generated by an older version of the CLI tool that roughly a third of teams hadn't yet upgraded. Any team on the older CLI attempting a staging deploy after 10:14 got a validation error with a message that didn't clearly indicate the actual cause, leading several teams to assume the problem was on their end and spend time debugging their own configs before escalating.

## Timeline
- 10:14 — schema validation change deployed
- 10:22 — first team reports staging deploys failing, files it as their own bug
- 11:05 — second, unrelated-seeming report; on-call starts noticing a pattern
- 11:40 — on-call correlates both reports with the 10:14 deploy, confirms via rollback test
- 11:52 — schema validation change rolled back
- 13:10 — full backward compatibility confirmed restored, incident closed

## Root cause
The validation change was tested against the current CLI version only. No test coverage existed for older-but-still-supported CLI versions, and there's no deprecation policy that forces teams off old CLI versions on any schedule — some teams were on a version eight months old.

## Contributing factor
The validation error message surfaced a generic schema mismatch rather than naming the specific incompatible field, which is why two teams initially misdiagnosed it as their own issue rather than escalating immediately.

## Action items
1. Add CLI-version compatibility matrix to the orchestrator's test suite — owner: Platform Infra, due in 2 weeks
2. Improve validation error messages to name the specific incompatible field — owner: Platform Infra, due in 1 week
3. Propose a CLI deprecation policy (max supported version age) to eng-leads — owner: Platform Infra, no committed date yet, needs cross-team buy-in first

## Not doing
Rolling back the underlying schema change permanently — the new schema is correct and needed; the incident was a rollout sequencing failure, not a design failure.

# Growth Team — Onboarding Flow A/B Test Results, Wave 3

**Analyst:** Growth Data Science
**Test:** New account setup flow, simplified vs. current
**Duration:** 3 weeks, 15% of new signups

## Setup

Two variants tested against current production onboarding:
- **Variant A:** reduced from 6 steps to 4 by combining profile setup and preference selection into a single screen
- **Variant B:** same 6 steps but with a progress indicator added (current flow has none)

## Results

**Variant A** (combined steps): completion rate +6.2pp vs. control, time-to-complete down 38 seconds median. Post-signup activation (defined as sending a first message within 24hr) was flat vs. control — the shorter flow didn't produce more engaged users, just got people through setup faster.

**Variant B** (progress indicator): completion rate +2.1pp vs. control, not statistically significant at our current sample size. Directionally positive, consistent with general UX literature on progress indicators reducing abandonment, but we'd need a longer run or bigger sample to call it confidently.

## Recommendation

Ship Variant A. The completion lift is clear and the flat activation number is fine — we weren't trying to change activation with this test, just reduce friction in signup itself. A separate test is already planned for activation specifically (different team, different surface).

Variant B: inconclusive, not shipping on this data alone. Could bundle the progress indicator into Variant A as a fast-follow and re-test the combination, low cost either way.

## Next steps
Rolling Variant A to 100% of new signups starting next week, monitoring for a week before calling it fully shipped. Growth PM to write the launch note for the team.

# Design Review — Settings Page Redesign, Round 2

**Presenter:** Settings team design lead
**Attendees:** Design crit group (rotating membership, ~8 people this week)

## What changed since round 1

Moved account security settings (password, 2FA, connected devices) out of a nested sub-page and into the top-level settings list — feedback from round 1 was that burying security settings two levels deep was actively bad given how often people land there specifically after a "suspicious login" email.

Notification preferences got consolidated from three separate toggle-heavy screens into one screen with grouped categories and a single master toggle per category rather than per-notification-type. Round 1 feedback was the granular version was technically more flexible but nobody used the flexibility and it made the page exhausting to scan.

## Crit feedback this round

- General agreement the security section move is correct, no dissent
- Notification consolidation got mixed reaction — one reviewer worried the master-toggle-per-category loses real functionality for the small number of power users who did use fine-grained control. Presenter's response: telemetry shows under 2% of users ever touched more than the category-level toggles anyway; proposing a "show advanced controls" expand option as a middle ground
- Visual density question — is the new settings list too sparse now that security isn't nested? One reviewer thought it looks unfinished. Presenter to explore a version with slightly tighter spacing before final review
- Someone asked about the account deletion flow, which isn't part of this round — separate workstream, different team

## Next steps
Incorporate the "show advanced controls" idea for notifications, mock the tighter-spacing option for the top-level list, bring both back for round 3. Targeting round 3 in two weeks.

# Vendor Eval — Analytics/BI Tooling Replacement, Finalist Comparison

**Requested by:** Jen Kwiatkowski, on behalf of Assistant Experience + two other teams
**Prepared by:** Data Platform team

## Context
Current BI tool (in place since 2023) is being sunset by its vendor end of next year. Need to pick a replacement before then; several teams' dashboards (including AE's core metrics dashboards) will need to migrate regardless of which tool wins.

## Finalists

**Tool A — incumbent's suggested upgrade path.** Pros: minimal migration effort, dashboards largely port over with light rework. Cons: pricing model changed substantially, would roughly double our current spend at present usage levels; also carries forward some of the same query performance issues teams have complained about for two years.

**Tool B — newer entrant, several peer companies have switched to it recently.** Pros: notably better query performance in our proof-of-concept tests, modern embedding options for dashboards inside internal tools. Cons: full migration effort, no direct import path from the incumbent, estimated 6-8 weeks of cross-team migration work.

**Tool C — build on open-source stack, self-hosted.** Pros: lowest ongoing cost, full control. Cons: highest upfront eng investment, ongoing maintenance burden falls on Data Platform specifically, team is not eager to take this on given current staffing.

## Recommendation
Tool B. The migration cost is real but one-time; Tool A's pricing change makes it a bad long-term bet regardless of lower migration effort, and Tool C shifts too much ongoing burden onto a team that didn't sign up for running BI infrastructure.

## Ask
Sign-off from each affected team's lead (AE, and the two others in the eval) confirming they can allocate migration time in Q4. Data Platform will coordinate a shared migration runbook rather than each team improvising its own approach.
