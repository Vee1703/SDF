# Design note (draft, incomplete): tenant-scoped configuration overrides

**Author:** d.okonkwo
**Status:** DRAFT — sections 4 and 5 not written, do not circulate outside the team
**Last edited:** 2026-08-30

---

## 1. Problem

We have eleven tenants with bespoke behaviour implemented as branches in serving code. Each one was reasonable at the time. Together they are a mess, and the mess has a specific shape: nobody can answer "what is different about tenant X" without grepping.

Concrete examples currently in `main`:

- Two tenants with a lowered default max output length, because their downstream renderer truncates.
- One tenant with a custom refusal string for a compliance reason.
- One tenant pinned to a previous model version, agreed in a renewal, expiring December.
- Four tenants with different tool timeout values.
- Three I found by grepping and cannot explain, all added before 2025-06.

The three I can't explain are the actual argument for this work. Someone made a decision, it survived, and the reason didn't.

## 2. Proposal

A tenant config layer: a declarative override document per tenant, versioned, with a schema, resolved at request admission. Serving code reads resolved config and has no tenant conditionals.

Requirements:

- **Every override has an owner and a reason field, both mandatory.** This is the point of the exercise. A config layer that lets you set values without saying why reproduces the current problem with better syntax.
- **Every override has an expiry date.** Default 12 months. Expiry means a ticket fires, not that the override silently drops — silent drops in production config are how you get an outage.
- Overrides are additive over a base config. No tenant can turn something off that isn't explicitly overridable.
- Resolution is deterministic and dumped in the request record so you can see what applied.

## 3. What is and isn't overridable

Draft allowlist. This is the contentious part and I expect to lose arguments here.

**Overridable:** output length caps, tool timeouts, tool allowlist, model version pin, refusal string, locale defaults, rate limit ceiling.

**Not overridable:** anything on the safety path, telemetry capture, retention tier. I'll defend the first of those at length if pushed; the other two I'd rather just not open, because "can tenant X be excluded from capture" is a question I don't want asked casually and the answer involves Legal.

**Undecided:** system prompt prefix. Two tenants effectively have one today, implemented badly. Making it a first-class override is honest about what we're doing, but it also makes it trivially easy to add and I think the friction is currently doing useful work.

## Test strategy: recorded fixtures vs. live contract tests

*Section 6 of the Platform Integrations handbook. Owner: r.sandoval. Last revised 2026-09-02.*

This section exists because we got this wrong and it cost us a Sev-2. Read it before you add a connector.

### The rule

**Every connector has both.** Fixtures for behaviour, a contract test for shape. If you only have one, you have the wrong one.

### Why fixtures alone are insufficient

A recorded fixture is a snapshot of a vendor response taken at some point in the past. Tests against fixtures verify that *our* parsing logic does what we think it does, given input we chose. That is a real thing to verify and fixtures are the right tool for it — they're fast, deterministic, run offline, and don't consume vendor quota.

But by construction a fixture cannot detect a change on the vendor's side. The fixture is what the vendor used to return. When the vendor changes, the fixture keeps passing, forever, silently. This is not a subtle failure mode and we walked into it anyway: INC-4471, three days of degraded scheduling across 31 tenants, and every connector test green throughout.

Note also what didn't catch it. Error rate didn't move — the vendor returned 200s the entire time. Latency didn't move. The alerting we had was on the transport, and the failure was in the payload.

### What a contract test is

A scheduled job that hits vendor **staging** with a small set of representative requests and asserts response shape against the schema we parse. Not behaviour — shape. Field presence, field type, nesting.

It runs daily, it fails loudly, and it is allowed to be flaky in the sense that a vendor staging outage will page nobody; it opens a ticket. A contract test that pages is a contract test people disable.

Requirements when you add one:

- Assert types, not just presence. Our incident was a field changing from object to string; a presence check would have passed.
- Assert against the shape the parser actually requires, not the shape the vendor documents. These diverge and the parser is the thing that breaks.
- Pin the request set. If the test's inputs drift, a failure doesn't tell you anything.
- Staging must be at or ahead of prod for schema. If the contract doesn't say so, the test is decorative — Osei is raising this at the Freeman & Voss renewal and the same question applies to every vendor we onboard.

### Runtime validation is not a substitute either

We now validate response shape at runtime on all connector paths and alert above a threshold. That's the third leg and it catches things the other two miss, because it sees production traffic rather than a representative sample.

But it's a detector, not a preventer. By the time runtime validation fires, customers are already getting degraded responses. The contract test's whole value is that it fires against staging before the vendor deploys. Don't let the existence of runtime validation become the reason nobody writes the contract test.

Expect the runtime validation to be noisy at first on any new connector. Vendors return null for empty collections, omit optional fields inconsistently, and change enum casing. Log these, set the alert threshold above the observed baseline, and write down in the runbook which ones you've decided to ignore and why. An alert you've silently agreed to ignore is worse than no alert.

### Checklist for a new connector

- [ ] Fixture suite covering parse paths, including malformed input
- [ ] Contract test against vendor staging, daily, opens a ticket on failure
- [ ] Runtime shape validation with a documented threshold
- [ ] Integrations alias subscribed to whatever the vendor calls its changelog
- [ ] Named owner for the vendor relationship, not just the code

The last item is not a joke. Item 3 on the 4471 action list was "subscribe to the vendor changelog," which took a day and would have given us seventy-two hours of warning, and the reason nobody had done it was that nobody was the person who would have.
