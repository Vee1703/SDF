**KES-778** — Tool timeout on `search_docs` is 8s and should not be

Project: Assist Platform · Type: Bug · Priority: P2
Status: In Progress · Assignee: t.wen
Created: 2026-09-11

---

**Description**

`search_docs` has an 8s timeout inherited from when it hit a local index. It hits a remote service now. p95 on that service is 6.2s and p99 is 11s, so we're timing out roughly 1 in 80 calls and the model handles it by telling the user it couldn't search, which is correct but not what anyone wants.

Raise to 20s. The user-visible cost is that a slow search feels slow; the current cost is that it silently doesn't happen.

---

**Comments**

**l.ferrand** · 2026-09-11
Agree with the change. Check whether the overall request budget accommodates 20s on this path before you ship it — if the outer deadline is 25s and the model wants two searches, you've moved the failure rather than fixed it.

**t.wen** · 2026-09-12
Outer is 45s, fine for two. Three would be tight. Shipping 20s and adding a metric on consecutive search calls so we know if three ever happens.

```
serving: bound retry budget per request

Retries were unbounded within the outer deadline, so a flapping
upstream could burn the whole 45s on one tool call and leave
nothing for the rest of the turn. Seen in the Halcyon incident
last week.

Adds a per-request retry budget (default 3, config
serving.retry.max_per_request) shared across all tool calls in
a turn, not per-call. Exhausting it surfaces as a normal tool
failure, which the model already handles.

No behaviour change when the budget isn't hit.
```

---

**PR #1420** — `serving`: bound retry budget per request

**a.mbeki** commented on `serving/retry.go` line 63

Shared-across-turn is the right call, but this decrements the budget on retries that succeed as well as ones that fail. Is that intended? A turn with three flaky-but-eventually-fine calls now has nothing left for a fourth call that actually needs it.

I'd only decrement on exhausted retries. Or keep it as-is and say why in the config comment, because the next person will ask this exact question.

> **r.sandoval** replied
